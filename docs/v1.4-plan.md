## The model (all of it in log space)

`g` is a monthly **log** growth rate; the number shown to a user is `e^g − 1`.
**Carry `g` at full precision and round only for display** — the briefed
`R_future = 1,264,831.30` only reproduces from an unrounded blended `g`; feeding the
rounded 3.881% back in gives 1,264,841.81.

```
g_personal   weighted least-squares slope of ln(cost) on months, w_i = exp(−age_i/6)
             requires ≥2 non-excluded observations spanning ≥14 days, else undefined
g_cat        ln(1 + categoryMonthly/100)
g_fxTrend    log slope of the FX series over the last 90 days, in monthly terms
g_fx         0.5·g_fxTrend + 0.5·g_overallCPI
g_prior      (1 − s)·g_cat + s·g_fx
λ            (n/(n+2)) · min(1, span/3)          // 0 when g_personal is undefined
g_product    λ·g_personal + (1 − λ)·g_prior, clamped to e^g − 1 ∈ [−5%, +25%]
g_domestic   λ·g_personal + (1 − λ)·g_cat        // g_cat alone when personal is undefined

R_now        with fxAtDate and a current rate:
               c_last · (FX_now/FX_at)^s · e^{(1−s)·g_domestic·ageM}
             otherwise: c_last · e^{g_product·ageM}
R_future     R_now · e^{g_product·m}
```

Time is measured in **mean months** of `30.436875` days for the regression and for
`ageM`. That constant is the model's, so it lives in `src/lib/rates/`, not in `dates.ts`
(whose `monthsBetween` is whole Persian months and is a different question).

Verified numerically before freezing — every briefed vector reproduces exactly:
`g_personal` 4.769%/mo · λ=0.5 → 3.881% · λ=5/7 → 4.260% · `R_now` 1,128,308.47 ·
`s=1` → 1,200,000 for any age · `R_future` 1,264,831.30.

and `costUpdatedAt`. The v1.3 localStorage override `sooda:inflation` becomes
`storeProfile.manualMonthlyPercent`, converted from annual percent to **monthly percent**
via `(1 + a/100)^(1/12) − 1`.

## Decisions and deviations

* **D1 — v1.4, not folded into v1.3.** v1.3.0 was already live and serving users when this
  addendum arrived; §0 decides the path and this is it.
* **D2 — the bundled fallback is a release-time snapshot, not a build artefact.** The pipeline
  lane wired `scripts/rates/fallback.mjs` as `prebuild`, so every build copied
  `public/data/rates.json` into the bundle. That silently defeats the `sw.js` gate above: the
  daily job commits the rates file to `main`, `main` is what Pages builds, so each day's rate
  would have changed a content-hashed chunk, the precache manifest, and therefore `sw.js` —
  an update prompt on every installed device, daily, for a number the app already fetches at
  runtime. The hook is removed; `npm run rates:fallback` is run deliberately at release time.
  Verified by building twice across a simulated refresh: only `data/rates.json` and
  `version.json` differ, both already `globIgnores`d.
* **D3 — the gate was measured, not assumed.** At the time of that test `src/lib/rates/load.ts`
  was reachable from nothing but its own test, so the two builds would have matched whatever
  the hook did. The finding stands on reading the dependency, not on the green result.
* **D4 — no invented data.** `public/data/rates.json` and `src/data/rates.fallback.json` ship
  entirely `null`. Three official sources were checked and are unreachable from cloud IPs; the
  one reachable endpoint is undocumented and ships disabled. `docs/rates.md` records exactly
  what a maintainer must type to fill each gap.
* **D5 — first paint held inside the v1.3 ceiling by moving work, not by raising it.** The
  direct wiring came in 325 B over. The check-in computation moved to `src/lib/checkin.ts`,
  the two new sheets behind `ShopSheets.tsx`, and the calculator's product link behind
  `CalcProductLink.tsx` — all reached only by dynamic import. Final: 125,968 B of 126,133.
