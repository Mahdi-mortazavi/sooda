# v1.5 — Interactive onboarding and the Learning Center

Frozen contracts. `lessons` and `ui` may not start until this file is committed; `coach` and
`sandbox` own the interfaces below and may not change their shape without updating it here.

## §0 — done before anything else

The rate defaults moved to a monthly basis (`3.4%/month`, Mordad 1405) and `rates.json` gained
real CPI figures. Recorded in the v1.5 §0 commit and in `docs/rates.md`; lessons do **not** read
any of it (see "tutorial rate" below).

## The event bus — frozen

Components announce what the user did; they never know a tour exists.

```ts
export type TourEvent =
  | { type: 'field:change'; field: string; value: string }
  | { type: 'field:commit'; field: string; value: number }
  | { type: 'chip:select'; group: string; value: string }
  | { type: 'mode:change'; mode: string }
  | { type: 'segment:change'; segment: string }
  | { type: 'sheet:open'; sheet: string }
  | { type: 'sheet:close'; sheet: string }
  | { type: 'result:shown'; mode: string }
  | { type: 'action'; name: string }
```

`emitTour(event)` is a no-op with no listener — one `if` and a return, so the cost to a user who
never opens a lesson is a branch, not a subscription. `field` and `group` values match the
existing field ids; `sheet` and `name` are kebab-case and listed in `src/learn/coach/events.ts`.

## Coach — frozen

```ts
interface TourCtx {
  emit(event: TourEvent): void
  /** A synchronously-readable snapshot. See the refresh rule below — it is load-bearing. */
  sandbox: SandboxState
  /** Re-reads the practice store into `sandbox`. Coach awaits this before every `expect`. */
  refreshSandbox(): Promise<void>
  /** Opens a sheet, switches a tab — anything a step needs in place before it can run. */
  navigate(to: { tab?: 'calculator' | 'products'; sheet?: string; mode?: string }): Promise<void>
}
```

**The refresh rule (amended after the coach was built).** `expect` is synchronous, but the
practice store is Dexie and therefore async. Left alone that is a trap: a step whose condition
reads the store rather than the event — "a product now exists" — would be evaluated against a
snapshot taken before the write landed, miss the event that actually satisfied it, and only pass
on the *next* unrelated event. So **Coach awaits `refreshSandbox()` before evaluating `expect`
for any event**, and lesson authors may treat `state` as current as of that event.

`expect` stays synchronous rather than widening to `boolean | Promise<boolean>`: most steps only
read the event, and making every lesson author write async predicates to fix a hazard in one of
them is the wrong trade.

```ts
interface DemoScript {
  /** Replayed by «نشانم بده» with the ghost finger. */
  actions: ({ target: string; type: 'tap' } | { target: string; type: 'type'; value: string })[]
}

interface LessonStep {
  id: string
  target: string                                   // matches data-tour="..."
  textKey: string
  placement?: 'auto' | 'top' | 'bottom' | 'start' | 'end'   // start/end are logical sides
  expect: (ev: TourEvent, state: SandboxState) => boolean
  demo?: DemoScript
  before?: (ctx: TourCtx) => void | Promise<void>
}
```

Rules the coach guarantees, and which reviewers check:

* the cutout stays interactive; everything outside it is `inert`;
* placement flips near a viewport edge and mirrors under `dir="rtl"`, and **never changes axis**:
  a step that asked to sit beside a chip is squeezed beside it rather than moved above it, where
  the author never looked. When neither side of the axis fits, the roomier one wins and the
  layout reports `fits: false`;
* the target is scrolled into view before the tooltip is measured;
* focus moves to the tooltip and returns to the target on advance;
* Escape and «رد شدن» both exit, always reachable;
* after 8s of inactivity the target pulses and a hint appears;
* under `prefers-reduced-motion` there is no ghost finger — a static ring and text instead.

## Sandbox — frozen

```ts
interface SandboxState {
  products: Product[]
  observations: Observation[]
  profile: StoreProfile | null
  lastResult: ResultDisplay | null
}
```

The practice store implements the **same repository interface** the real one does, so no
component knows which it is talking to.

**Repository injection (added after the sandbox was built).** `src/lib/products.ts` and
`src/lib/observations.ts` now export `createProductRepository(db)` and
`createObservationRepository(db)`, with the existing named exports kept as thin bindings to the
real database so nothing else changed. This is not tidiness — it is the difference between the
promise holding and only appearing to:

* the sandbox's guarantee covers **its own surface**. Components call `lib/products.ts` directly
  through the module-level real `db`, so a component rendered during practice would write to the
  shopkeeper's real data no matter how isolated the sandbox is;
* so **`ui` must provide the repository through context**, and hand components
  `session.repository` while practice is running. A component that imports the bound exports
  directly is a bug, and the offline-and-privacy reviewer checks for exactly that;
* the factories also take an optional clock (`createProductRepository(db, () => now)`), so a
  lesson can pin an instant and get the same challenge answer on every run — without it the seed
  is dated at one moment and a row the learner writes at another, and any question about how old
  something is drifts with the wall clock;
* and the practice store must use `createProductRepository(practiceDb)` rather than a
  hand-written copy. A mirror that merely *matches* the real logic can drift from it; a lesson
  must run the same code the shop runs, including which writes count as a new price reading.

**The check-in was a third hole (found by `lessons`, fixed during Phase 3).** The injection above
covered the two repositories, but `src/lib/checkin.ts` read the module-level real `db` and the
bound exports of `observations.ts` directly. Lesson 6 renders the check-in sheet on the real UI,
so practice would have asked the shopkeeper about their own products and judged the learner
against them. `computeCheckIn(rates, source?, clock?)` now takes a `CheckInSource` — the four
reads a pass makes — defaulting to the real shop, and `useCheckIn(rates, enabled, source?)`
threads it. `session.repository` satisfies `CheckInSource`. The app-icon badge is set only on the
real path: a count badged from a tutorial means nothing once the practice store is deleted, so
`ui` calls `reload()` on exit to recompute it. `src/lib/checkin.test.ts` covers this.

The lesson generalises. The repository interface covers what goes through a repository, and
nothing else: localStorage (the draft, the rate override, `sooda:last-version`), the PWA badge,
the share link, the CSV export and backup/restore all sit outside it. Each has to be checked on
its own, and the offline-and-privacy reviewer is asked to do exactly that.

Non-negotiable: during practice nothing reads or writes
the real `history`, `basket`, `products`, `observations`, `storeProfile`, the draft, the badge
count, or a share link. `sandbox` owns a test that runs every lesson end to end and asserts each
real table is byte-identical afterwards.

## The tutorial rate

Lessons pin **3%/month**, independent of `rates.json`, so a challenge answer cannot change when
the maintainer updates a figure. Every lesson that shows a rate says so in words
(«در این تمرین فرض می‌کنیم قیمت‌ها ماهی ۳٪ گران می‌شوند.»). `scripts/lesson-examples.mjs`
computes every expected answer from the real engine at that pinned rate, and a test asserts the
lesson files still match its output — the same guard `docs-examples.mjs` gives the READMEs. Both
now run as `--check` in `npm run verify` and in the deploy workflow, so a committed figure that
no longer matches the engine fails the build rather than waiting for a reader to believe it.

`TUTORIAL_ROUNDING_STEP = 1000` is pinned beside the rate, and is **never written to the user's
own `sooda:rounding`**. The demo shop's prices are built on 1,000; with the user's rounding off,
every figure a lesson shows would disagree with the shop it is showing.

## Progress store

`localStorage['sooda.learn.v1']`:

```ts
{ onboardingDone: boolean, goals: GoalId[],
  lessons: Record<LessonId, { status: 'new'|'progress'|'done'|'passed'; step: number; passedAt?: number }>,
  tipsSeen: string[], tipsEnabled: boolean }
```

Every access is wrapped; with storage unavailable the tutorial still runs, it just forgets. It
rides in backup/restore, and "Erase all data" clears it.

## Gates

* First-paint growth **≤ 1 KB gzip** over the v1.4.1 ceiling (127,157 B). Only the first-run
  check, the `?learn` parser and the "?" buttons may be in the entry chunk.
* Every lesson step's `target` exists in the rendered tree — asserted by a test, not by eye.
* Smoke: onboarding end to end; every lesson including its challenge; one lesson driven only by
  «نشانم بده»; RTL and LTR; exit mid-lesson with real data intact.
* Onboarding ≤ 60s and each lesson ≤ 90s, measured in the smoke run and reported.
* No Lighthouse regression against v1.4.1 on the same machine.

## Decisions

* **D1 — a separate Dexie database, not an in-memory repository.** `sooda-practice`, deleted on
  exit. The alternative duplicates Dexie's live-query semantics in a second implementation, and
  a sandbox that behaves subtly differently from the real thing teaches the wrong lesson.
* **D2 — no tour library.** The overlay is ~200 lines; a dependency would cost more than that in
  the entry chunk and would not mirror for RTL.
* **D3 — steps advance on events, never on timers.** A step that advances on its own is a
  slideshow, and the brief rules those out.
